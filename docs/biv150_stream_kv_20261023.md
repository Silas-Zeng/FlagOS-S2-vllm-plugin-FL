# BI-V150 BF16 decode streaming K/V loads

Base: team main3283672, verified through the authenticated API after direct Git
fetch timed out. No official upstream version is upgraded. This candidate changes
only cache policy on the existing audited BF16 GQA operator. No model weights,
KV dtype/layout, softmax arithmetic, launch width or service parameter changes.

The compiler IR confirms native BF16 matrix instructions and already fused PV
accumulation. Original BF16 loads use COREX kop flag0; explicit.cv leaves query
loads at flag0 and changes64 K/V load sites to flag3 in the sampled compilation.
Source/assembly hashes alone are not counted as proof of instruction change.

Five alternating timing rounds per shape show bit-exact.cv outputs, with minimum
speedups1.0139x at B64/KV4096 and1.0115x at B32/KV16384; B31/KV16896 minimum1.0217x.
However B8/KV1024 is slower, approximately0.961x. A separate.cg search is positive
for that small shape. The candidate chooses.cg for captured batch<=8 and.cv for
larger captured batches; this is a batch-static operator choice compatible with
FULL_DECODE_ONLY, not a Python sequence-length check frozen incorrectly by capture.
This heuristic is based on tested shapes, not claimed universally optimal.

The production wrapper checker must verify both selected policies and bit-exact
outputs over mixed lengths, padded rows, tail pages, shuffled pages and long KV.
Full Level3 and warmed single-round4K/16K serving acceptance remain pending.
Operator improvements are small and are not an end-to-end+20% claim.

Production wrapper9b9cc4c passed all eight cases. Selected policies match the
batch-static rule; outputs are bit-exact, no register spill and shared memory
unchanged. Measured speedups:1.0151x B64/KV4096,1.0118x B32/KV16384,
1.0223x B31/KV16896,1.0179x B8/mixed KV1024; B1/KV100 is effectively unchanged.
Full combined precision/warmed throughput run is live on the owned instance.
The source checkout and official service arguments are recorded by its manifest.

## One change and one falsifier

In both full PAGE16 and masked-tail paths, move only `V = tl.load(...)` and
`value_scale = tl.load(...)` from immediately after K loading to immediately
after `running_sum`, before PV. The BF16 conversion of V was already in the PV
expression and stays there. Preserve exactly:

```python
tl.dot((probability * value_scale[None, :]).to(tl.bfloat16), V.to(tl.bfloat16))
```

No packed-i32 representation change, paired shared store, fake dependency,
constant-zero arithmetic, P8, K32, cache-format change, or production hook.
PAGE16, BF16 QK, softmax, segmentation, natural-log maxima handoff, reducer and
every original guard remain intact. Allocation stays16KiB/page; no KV capacity
is reclaimed. Shared/barrier/store layout is a preservation target, not a
claim based on moving source lines.

This is a source-scheduling falsifier. The compiler can hoist the loads/unpack
again; later loads can also lose useful latency overlap. No compilation or
device execution has been performed for this candidate. Resource reductions
would not prove a speedup. PR73/4a full-path numeric-diagnostic timing has priority.

## CPU evidence and guarded entry points

```sh
PYTHONDONTWRITEBYTECODE=1 python3 tools/check_biv150_v8_late_read_cpu.py
PYTHONDONTWRITEBYTECODE=1 python3 tools/check_biv150_v8_bf16p_cpu.py
PYTHONDONTWRITEBYTECODE=1 python3 tools/bench_biv150_v8_late_read.py --case ragged
```

[cpu.json](evidence/v8-late-read-20261027/cpu.json) records exact producer AST
inverse, independent-load dependency checks, the exact frozen4a benchmark AST
inverse, all19 archived SHA checks, inherited writer/codec/default/baseline
diagnostic falsifiers and additional source/lowering/pre-launch mutants. The
new source is never imported as Triton during CPU checks. A deliberately
reordered, non-executable text fixture is only a positive parser test; it is
not compiled GPU IR or evidence that the candidate mechanism works. Both full
and tail of actual b8 IR correctly fail the mechanism gate.

Root alone may schedule this **after66 ends**, with a new private cache/output,
and after the higher-priority4a diagnostic. The first minimal request is:

```sh
python tools/bench_biv150_v8_late_read.py --compile-only --case ragged --out NEW_COMPILE_OUT
```

This explicit mode does JIT and module-handle creation, but contains no kernel
launch: only tiny uninitialized pointer stubs, the exact frozen packed/scratch
ABI, and `warmup`. It exports actual BF16 baseline, frozen V8 and late V8
TTGIR/LLVM/ASM/backend metadata and resources for the same specialization.
Full and tail must retain BF16 MMA, eight packed V loads,32 byte extractions,
32 i8→BF16 conversions, and place extraction/conversion **after all softmax
exp2 instructions**. The checker also compares shared bytes, V blocked/shared
layout definitions, shared-store/barrier/conversion/MMA counts against frozen V8.
Registers/spills/use_sme are reported without a speed claim. Missing debug
mapping or unfamiliar lowering fails closed for manual review. The checker is
deliberately conservative; it does not substitute for inspecting actual shared
addresses or establish latency/occupancy.

If early unpack remains, save the failed proof and stop before execution/timing.
Do not add fake dependence to force scheduling. If the ragged mechanism passes,
root can separately request the same compile-only phase for steady4k/steady16k.
Only cases included in a successful exact-source proof can be executed:

```sh
python tools/bench_biv150_v8_late_read.py --run-gpu --ir-proof NEW_COMPILE_OUT/compile-proof.json --case ragged --out NEW_CHECK_OUT
# Only after reviewing the mechanism, for explicit finite candidate diagnostics:
python tools/bench_biv150_v8_late_read.py --run-gpu --numeric-diagnostic --ir-proof STEADY_COMPILE_OUT/compile-proof.json --case steady4k --case steady16k --out NEW_DIAGNOSTIC_OUT
```

Before its first actual launch, the wrapper warms up the real runtime arguments
and requires the exact proven compiled hash and TTGIR/LLVM/ASM SHA; an ABI or
specialization mismatch stops before launch. The separate entry point adapts
the pinned4a probe only by kernel filename and this pre-launch check; reversing
those two edits reproduces its entire AST, including all original numeric,
writer/codec/slot/unmapped/Graph guards and baseline hard gate. Default remains
strict. Diagnostic mode can time only finite candidate precision failures after
baseline and every hard guard pass; it never sets `precision_gate=true`.
No model105, TTFT or formal service throughput has been tested or claimed.

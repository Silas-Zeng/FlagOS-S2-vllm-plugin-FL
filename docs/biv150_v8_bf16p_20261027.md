# V8 storage with BF16 weighted P and BF16 PV

This independent CJJ experiment starts from team main
`241220723a09061c182764f8f738e5ec01190367`. It retains the pinned GQA producer's
BF16 Q/K, PAGE16 loop, softmax, segment bounds, partial units and original
reducer. Only the cached V representation and PV operands change:

```python
tl.dot((probability * value_scale[None, :]).to(tl.bfloat16),
       value_codes.to(tl.bfloat16))
```

Each cached token/head has 128 signed INT8 V codes and one FP32 scale. All
integers in [-127,127] are exactly representable in BF16. P*scale rounds once to
BF16 before the original BF16 tensor-core dot. The normalization denominator
continues to sum the original unweighted FP32 probabilities.

The producer does not quantize P to INT8, compute a per-P-row amax/floor, combine
two pages into a K32 tile, invoke integer MMA, or reconstruct every V element as
code*scale. Closed PR55's directly quantized INT8 P×V path measured only
0.40–0.52x for the complete component and is not reused. The V codec and
diagnostic writer are reused from that closed experiment; this branch has no
dependency on an unmerged production change.

## Allocation and integration boundary

The prototype retains a 16,384-byte allocation per page, matching the original
packed BF16 cache shape `(nBlocks, 2, 16, 2, 128)`. Within each diagnostic page:

| Byte offsets | Contents |
| --- | --- |
| 0–8191 | Original BF16 K |
| 8192–12287 | INT8 V codes |
| 12288–12415 | FP32 scales, `(slot, head)` order |
| 12416–16383 | Untouched padding |

The scale view is FP32 with strides `(4096,2,1)` and a 12,288-byte offset. The V
view is INT8 with strides `(16384,256,128,1)` and an 8192-byte offset. Effective
payload is 12,416 bytes/page, or 75.78125% of the original K+V payload; this is
only a theoretical read-payload count. Physical capacity reclaimed is **false**.
Both control and candidate caches remain allocated in the component harness.
A future 256-byte-aligned compact allocation would be 12,544 bytes/page, but
requires coherent writer, prefill, decode, backend, copy/offload and graph
integration. That integration and any resulting capacity or speed benefit have
not been demonstrated. Typed BF16 copy paths must not reinterpret encoded bytes.

## CPU evidence

`docs/evidence/v8-bf16p-20261027/cpu.json` records CPU-only checks. No GPU,
remote machine, dependency installation, or global-package modification was used.

- The original GQA source SHA256 is pinned to
  `2596cc09caf9b5b38b49755ae9af41ebdcf59a1d5ad889fc8e9319d1584438d1`.
  Removing the two V-scale loads and restoring the two PV expressions yields a
  producer AST identical to the baseline, including the PAGE16 loop and tail.
- Layout checks verify disjoint K/V/scale/padding bytes and exact BF16
  representability of all 255 signed codes. They do not execute the device writer.
- An independent FP64 global-softmax × Vcode × scale oracle shares no streaming
  or segment recurrence. It agrees with the ideal PAGE16 scalar recurrence for
  72 length/segment combinations, including zero, page tails, 4K and 16K.
- A separate scalar BF16(P*scale) rounding model satisfies a sum-of-absolute-terms
  error bound. Its measured maximum absolute difference is 0.01422 on deliberately
  broad synthetic scales. This is neither a GPU tolerance pass nor a model score;
  it does not emulate FP32 dot accumulation or device denormal behavior.

## Validation hardening before the first GPU run

The initial harness could hide a missing graph writer behind an eager write,
and its codec checks reused device scales/cache. Those checks have been replaced;
the initial revision is not the version to run for first GPU qualification.

The revised harness retains immutable original CPU BF16 K/V, the CPU slot map,
and every changed query/new-token pair. The CPU expected cache is built only
from those originals and the supplied new tokens. Both FP64 attention oracles
consume that CPU cache, never device-written K, V codes, or V scales. The V8
oracle independently computes per-vector maxabs/127, rounds the scale to FP32,
applies the zero-vector scale 1 and minimum-normal clamp, and computes signed
half-away codes. The scalar checker validates device scales independently within
one FP32 ULP (constant-reciprocal lowering); zero/clamped scales must be exact.
A one-code difference is allowed only within four FP32 ratio ULPs of a half tie,
using the independent CPU scale. It cannot validate scale 1e20 with zero codes.

Each post-capture pattern changes both new K and new V. Before replay, the
harness snapshots the allocation and poisons all mapped K/V/scale bytes plus
output/scratch/max/sum. It replays **before** any eager writer, checks target K
exactly and target V/scales against CPU inputs, and checks every unmapped byte
against the snapshot. Only then does it run eager and check its writes and exact
output equality. This covers every writer target and every unmapped byte for all
cases. Bulk-codec validation covers every vector on ragged cases and sampled
normal-range pages plus all writer targets on the large cases. CPU input fixtures
are saved beside results as `*-cpu-inputs.pt` (full ragged or sampled steady pages,
with original page IDs, slot mapping, table, lengths and all changed inputs).

Consumption precision is now a hard component gate: each complete query output
must have relative RMSE <=2% against original-BF16 control output. The same gate
is independently checked against the original-BF16 FP64 oracle on **all** ragged
rows and sampled large-case rows. Zero-reference rows require exactly zero output.
The separate kernel-correctness check against the CPU V8 FP64 oracle still uses
`abs_error <= .005 + .005*abs(reference)` pointwise. Every failure raises and leaves
`completed=false`; timings follow successful checks only. The 2% consumption gate
is a local experimental filter and does not establish model precision.

The shared stdlib validation gates have CPU falsification fixtures. They reject
16 mutants, including an omitted or partial writer after cache poison, stale tokens,
unmapped padding writes, non-half-boundary code errors, wrong/clamp/zero scales,
and self-consistent huge scales with zero codes. They accept the two adjacent
codes only at explicit signed half ties. Zero-output and >2% consumption faults
also fail. Static CPU checks prove cache poison precedes replay, writer validation
precedes eager, and both attention reference calls receive CPU expected inputs.
These are validation-code tests; actual GPU writer/Graph behavior is still unrun.

## Prepared GPU entry, not yet executed

The opt-in benchmark preserves actual packed KV strides, table pitch 8192,
narrowed segment scratch, the shipping reducer, and hash checks for the actual
4K/B64 and 16K/B32 baseline kernels. It prepares writer+producer+reducer timing,
separate attention-only timing, independent FP64 device-output checks, shuffled
pages, lengths 0/1/15/16/17/31/32/33 and 63/64/65/127/128/129/256/257, invalid
slot no-write checks, two changed input patterns, poisoned output/scratch graph
replay, and byte-padding/code checks. These checks are **pending**, not CPU results.
The writer control is this diagnostic writer, not vLLM's integrated writer cost.

When the machine owner schedules an idle GPU window in the designated existing
Python environment, the prepared command is:

```bash
python tools/bench_biv150_v8_bf16p.py --run-gpu --warps 1 \
  --out /tmp/biv150-v8-bf16p-w1-UNIQUE
```

The harness checks the service port and GPU process list, but those checks are
not an experiment reservation. `--warps 2` is a separately recorded bounded
candidate. Inspect actual compiler IR to establish BF16 MMA and conversion costs.
No GPU compilation/numerics, complete-model 105-question precision, TTFT, 4K/16K
service throughput, or compact-cache integration has run. `precision_gate=false`,
`official_score=false`; this experiment must remain Draft and must not merge on
CPU or component evidence alone.

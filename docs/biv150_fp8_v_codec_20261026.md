# Software FP8 V-cache codec experiment

The current16K profile identifies the GQA producer as a major measured cost. Prior original INT8 KV experiments(PR49) lost throughput across three bounded variants, with expensive K/V conversion, scales and increased registers. That result does not prove an FP8 or V-only representation will lose; it also does not establish bandwidth saturation. This branch tests a different mechanism: keep K in BF16, encode only V with a fixed-scale E4M3 byte representation and decode directly to BF16 by integer fields or a512-byte BF16 lookup table. No native FP8 instruction or existing framework FP8 switch is assumed.

## Numeric contract

The E4M3 field interpretation follows [Micikevicius et al., FP8 Formats for Deep Learning, Table1](https://arxiv.org/pdf/2209.05433): sign/exponent/mantissa widths1/4/3, exponent bias7, finite maximum448, minimum normal2^-6, minimum subnormal2^-9 and signed NaNs at absolute code127. This experiment explicitly chooses nearest-even rounding, saturation for finite overflow, and signed canonical NaN for nonfinite inputs. Those conversion choices are distinct from defining the byte format. The paper discusses scaling; fixed scale1 here is an unqualified experiment and may lose model precision or saturate actual V values.

CPU reference enumerates mathematical representable values and chooses the nearest with ties-to-even; it does not reuse the integer candidate. Every65536 BF16 bit pattern matches that independent oracle, including65280 finite inputs and256 special patterns. All256 decoder bytes and126 exact midpoint ties pass; negative zero is preserved. The exhaustive input space contains30526 finite overflows because BF16 spans a much larger range; this is not a model V distribution. Original CPU report is under docs/evidence/fp8-v-codec-20261026/.

The self-developed Triton codec uses BF16 bit fields for encoding and either bit-field BF16 reconstruction or a lookup for decoding. The GPU checker is inert unless --run-gpu; planned checks cover the entire finite BF16 space, all256 codes, default/side streams, changed-input poisoned Graph and partial-block canaries. It refuses an occupied GPU/9031 port and records frozen source/driver identities. No GPU check has run yet.

## Scope and remaining work

There is no serving hook, allocator or model change. Component-only writer and fused decode consumer prototypes are now prepared, as detailed below; they have no GPU qualification. No throughput, attention numerical,105-question or capacity result exists. BF16 K plus one-byte V would reduce payload read/storage bytes to3/4 before metadata, but this is theoretical and does not establish saved physical capacity or speed. An initial model prototype can retain original allocation and encode V inside its region, explicitly claiming no capacity recovery. Both prefill and decode, cache writes and all fallback consumers must agree on the representation; a decode-only switch is invalid.

Next gates: actual codec compilation and bit conformance; a fused GQA V consumer retaining the verified baseline geometry/hash and independent CPU FP64 original/quantized references; actual writer cost and changed-input/ragged Graph; then consistent prefill/decode integration, actual V range statistics, full105-question precision and fixed4K/16K/TTFT qualification against the latest valid team baseline. ## Prepared fused V consumer and writer

The component prototype preserves the shipping segmented producer at sourceSHA2596cc09...; a CPU inverse proof removes only the new V reconstruction sites/parameters and exactly recovers the original function. QK, softmax recurrence, segment maxima/output and unchanged reducer math remain intact. Two bounded decode mechanisms use the same E4M3 representation: integer BF16 bit reconstruction and512-byte lookup. No K conversion, FP32 cache scales or materialized BF16 V cache is added.

For the initial probe, physical allocation intentionally remains the original16384bytes/page. K retains8192 BF16 bytes at the original addresses. V uses4096 encoded bytes at offset8192, followed by4096 unused bytes. CPU address checks prove unique, disjoint, bounded K/V/padding for multiple pages; no capacity is reclaimed. The original BF16 control and encoded candidate allocation are both retained. This layout is a probe, not an implemented model representation.

The original slot writer copies K and encodes V for valid slots; negative/out-of-range slots return without writes. The component benchmark targets B64/4K, B32/16K and ragged B8/257 with packed strides,8192-wide page tables and narrowed16-wide scratch. Baseline4K compiled hash must match641478e6. It plans independent CPU FP64 original/quantized-V references, changed/poisoned Graph, invalid-slot raw-byte preservation, unchanged K/padding and CPU-exact V code checks. Timings include the experimental writer, producer and unchanged reducer in three alternating rounds; attention-only timing and compiler resources are separate. The control writer is ours and is not claimed as measured vLLM writer performance.
